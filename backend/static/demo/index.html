The model routes. It never authorizes.

An internal HR assistant where five roles ask the same chat box for payroll, attendance, leave, analytics and audit data — and each one gets a different answer, because access control lives in the backend rather than in a prompt.

A planner agent reads the request and picks one of four specialist agents. Those agents choose a tool. Everything after that is plain Python reading permissions out of PostgreSQL.

Every agent can see all seventeen tools and is instructed never to refuse. Refusing is not their job — the gates below decide, and they decide the same way whether the request came from the chat box or the console.

Who holds what

Seeded baseline in rbac/permissions.py. At request time these are read from the role_permissions table, never from the file — which is what makes the runtime changes in Scenario 02 take effect on the very next message.

Five scenarios

Each one exercises a different gate, and they build on each other: 02 grants what 03 then narrows.

# The single enforcement point. Every tool call in the system goes through it.
def execute_tool(tool: Tool, ctx: ToolContext, tool_input: dict) -> ToolResult:
    """RBAC check first, database access second.

    Raises PermissionDenied when the check fails, so no query is ever issued.
    """
    check_permission(ctx.principal, tool.required_permission)
    return apply_field_policy(tool, ctx, tool.handler(ctx, tool_input or {}))
backend/rbac/service.py:136↗ 
def check_permission(principal: Principal, required_permission: str) -> None:
    # principal.permissions was read from PostgreSQL for the authenticated user —
    # never from the request body, the planner, or the LLM's tool arguments.
    if not principal.has(required_permission):
        raise PermissionDenied(required_permission, principal.role)

Why it is built this way. The analyst's agent genuinely tried to call get_payroll — it was never handed a filtered tool list. Pre-filtering tools per agent would put the language model in charge of access control, and a model can be talked out of a decision. The check sits in front of the handler instead, so a denial costs one function call and the database is never touched.

    """Grant or revoke a role's access to one tool by editing role_permissions."""
    # Guardrails, all server-side — the model cannot argue past any of them.
    if role.name in PROTECTED_ROLES:
        return ToolResult(summary=f"The '{role.name}' role is protected …")

    if tool.required_permission == PERMISSIONS_WRITE:
        return ToolResult(summary=f"'{tool.name}' controls RBAC itself and cannot "
                                  "be granted or revoked from chat.")
What stops it going wrong
  • The five write tools are gated on permissions:write, held by super_admin alone — and they run through execute_tool like every read tool, so an unauthorized caller never reaches the handler.
  • super_admin is a protected role. Without that, a super admin could revoke their own permissions:write and lock everyone out of RBAC management with no way back short of re-seeding.
  • The write tools cannot grant themselves. No role can talk its way into the ability to hand out permissions.
  • An unknown role or tool name is explained back with the list of valid ones, rather than silently doing nothing and reporting success.
  • Granting a dataset does not grant every column of it — if columns are still withheld the reply must say so, carried in a dedicated caveat field the responder is forbidden to drop.

Why it is built this way. The access-control page and the chat box post to the same tools. One implementation, one permission check, one audit trail — so the conversational path cannot drift into being a weaker version of the console, and there is no second code path to keep in sync.

Scenario 03 Gate 4 · column policy

Holding the dataset is not the same as seeing all of it

HR has just been granted payroll. They now see base pay — and not the bonus and deduction breakdown, because column access is a separate grant. The interesting part is what happens when someone tries to get the withheld figure back by arithmetic.

What the user sees
HR Allowed 2 columns withheld

Show me this month's payroll.

  • rbac → ALLOWED · payroll:read
  • database → 12 rows
  • fields → bonus, deductions stripped

A table of base salary and net pay, closing with a clause naming what is missing — and the responder is instructed never to estimate a withheld value.

Any role Closure applies

Withhold base salary but leave bonus, deductions and net pay.

  • net_pay + deductions − bonus
  • = base_salary, exactly
  • → all four withheld

A redaction that can be undone with one subtraction is not a redaction. The policy closes over the arithmetic before any data leaves the server.

# The four money columns satisfy net_pay = base_salary + bonus - deductions, so any
# three give the fourth. Each names the other three: withholding one withholds all
# four, and there is no arrangement that hands a role three and calls the fourth
# private. Withholding *two* is still allowed — that leaves only their difference
# derivable, which is how HR sees base pay without the bonus/deduction split.
FieldSpec("base_salary", "Base salary", reconstructed_by=("bonus", "deductions", "net_pay")),
FieldSpec("net_pay",     "Net pay",     reconstructed_by=("base_salary", "bonus", "deductions"),
                                       derived=("total_net_pay",)),
backend/rbac/datasets.py:77 — DatasetSpec.effective_withheld↗ 
withheld = {spec.key for spec in self.fields
            if not spec.locked and spec.key not in granted}

# Close over reconstruction: when every column that determines a withheld field
# is visible, the withheld figure is one subtraction away — so withhold those too.
while changed:
    for key in list(withheld):
        siblings = [by_key[name] for name in spec.reconstructed_by if name in by_key]
        # Only a *complete* set reconstructs the field. If one is already
        # withheld the sum cannot be solved, and the rest stay visible.
        if not siblings or any(sibling.key in withheld for sibling in siblings):
            continue
        for sibling in siblings:
            withheld.add(sibling.key)

Why it is built this way. Stripping happens in execute_tool, after the handler and before the agent — so a column the role may not see never enters the model's context and cannot leak through a paraphrase. Aggregates computed from a withheld column go with it, so the figure cannot be read back off a total either.

backend/tools/base.py:98↗ 
def visible_employee_ids(ctx: ToolContext) -> list[int] | None:
    """Row-level scope, read from the caller's role: all | department | team | self.

    This is scoping, not authorization — a role still needs payroll:read to reach
    payroll at all; this only narrows *which rows* it gets.
    """
    scope = ctx.principal.row_scope
    if scope == SCOPE_ALL:
        return None                              # no row restriction

    if ctx.principal.employee_id is None:
        return []                                # no anchor to scope from

    # SCOPE_TEAM: the caller plus their direct reports.
    reports = ctx.db.scalars(
        select(Employee.id).where(Employee.manager_id == ctx.principal.employee_id)
    ).all()
    return [ctx.principal.employee_id, *reports]

Why it is built this way. Scope resolves against the employee row the login is linked to, not against anything the request carries — so a supervisor cannot widen their own reach by rephrasing the question. A login with no linked employee record sees nothing under a narrow scope, because there is no anchor to scope from.

# 0. Model gate. A model the role does not hold is refused here — no provider is
#    called, and the refusal is audited like any other RBAC decision.
try:

        check_model_access(principal, requested)

Why it is built this way. A permission refusal must never depend on a model being available. A role with no model at all has nothing to write its own refusal with, so that text is deterministic Python — and denials for a locked model are audited under a pseudo-permission (model:claude-opus) so they read the same as every other decision in the trail.

Stage by stage

Every stage cites the file it lives in. The citations open that file on GitHub at the line the stage starts — they track main, so they follow the code as it changes.

Stage 00load_principal() backend/rbac/service.py:102↗

The JWT identifies a user; everything RBAC needs is then read from PostgreSQL for that user — role, permissions, allowed models, row scope, column access. Nothing here reads a role, permission or model supplied by the frontend, so a forged request body changes nothing.

Gate 1check_model_access() backend/rbac/service.py:142↗ called at executor.py:134↗

Model choice is RBAC, not configuration. A model the role does not hold in role_models is refused before any provider is called — so a denied request costs nothing and is audited under model:<key>. On success the picked model heads a fallback chain of the rest of the role's models.

Stage 01make_plan() backend/agents/planner.py:86↗

The planner names the intent and routes to exactly one specialist agent. It is told explicitly to route on the subject of the question, not on whether the user should be allowed to ask it. Greetings and questions about the assistant itself route to "none" and are answered without touching a tool.

Stage 02select_tool() backend/agents/llm.py:136↗ prompts at role_agents.py:30↗

The chosen agent picks one tool and fills in its arguments. All four agents are handed the same seventeen tools and instructed never to refuse, never to mention permissions, and never to ask the user to confirm their access level. What differs between them is specialisation — which data source they reach for first.

Gate 2check_permission() backend/rbac/service.py:136↗ called at base.py:197↗

The enforcement point. Every tool declares one required permission, and the check runs inside execute_tool before the handler — so an unauthorized caller never reaches a line of query code, and the database is never touched on a denial.

Stage 03tool.handler() backend/tools/registry.py:20↗ writes at admin_tools.py:156↗

The only path from an agent to the database. Read handlers query; the five write handlers edit role_permissions, role_models, role_field_access or role_data_scope — which is how a super admin changes access from the chat box.

Gate 3visible_employee_ids() backend/tools/base.py:98↗ scopes at datasets.py:279↗

Row reach, resolved against the employee record the login is linked to: every employee, one department, the caller plus their direct reports, or the caller alone. Gate 4apply_field_policy() backend/tools/base.py:171↗ closure at datasets.py:77↗

Columns the role may not see are stripped from the result, along with any aggregate computed from them — and along with sibling columns that would reconstruct them by arithmetic. This runs after the handler and before the agent, so a withheld figure never enters the model's context in the first place.

Stage 04log_tool_request() backend/rbac/audit.py:12↗

Every decision is recorded — who, which role, which agent, which tool, which permission, allowed or denied, and why. Denials are logged as fully as successes, which is what makes the trail worth reading.

The planner turns the outcome into prose. It is instructed to answer only from the data provided, to name withheld columns rather than estimate them, and on a denial to say plainly which permission is missing without speculating about what the data would have shown. If no model is reachable, a deterministic refusal is used instead.

Two decisions worth defending

Agents are not given restricted tool lists

All four agents see all seventeen tools. Ask the analyst agent for salaries and it will genuinely reach for get_payroll — Gate 2 is what stops it.

Filtering each agent's tools would look tidier and would be worse: it puts the language model in charge of access control, and it hides the boundary this system exists to demonstrate. A model can be talked out of a decision. A permission check cannot.

Four gates, not one

"Can this role read payroll?" is one question out of four. The others are which model may answer, how many employees' rows are in reach, and which columns of the row come back.

Collapsing them into a single permission check is how systems end up handing a role a table it half-owns — or handing out three of four money columns and calling the fourth private.
