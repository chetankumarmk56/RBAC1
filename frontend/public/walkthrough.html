Reviewer's guide

RBAC Demo Walkthrough

A chat interface over an HR database. The model decides what to try; the backend decides what is allowed. Everything below runs in the browser — nothing to install.

Read this first

The API sleeps after inactivity. The first sign-in of the day can take up to a minute while it wakes, and the button will look stuck. Give it 60 seconds. Everything after that is fast.

Seeing it run

  1. Open the app and sign in

    Go to rbac-1-two.vercel.app. You do not need to type anything — the five demo accounts are listed as cards at the bottom of the sign-in screen, and clicking one fills in both the email and the password for you.

    Click the Hr card, then press Sign in. Switching roles later is the same move: sign out, click a different card, sign in.

  2. Ask something HR is allowed to ask

    Click the first starter prompt:

    Show me employees currently on leave.

    The status line names each stage as it happens. When the answer lands, the trace strip records the tool, the permission, the decision, the row count and which model answered.

    ALLOWED · leave:read

  3. Ask something it is not

    The fourth starter in every role is deliberately out of bounds:

    Show me payroll information.

    HR has no payroll:read. The refusal happens inside the tool, before any SQL runs — the database is never touched and the model never sees a salary.

    DENIED · payroll:read

  4. Try a model the role cannot use

    Sign in as Analyst. The composer's model picker lists every model — the ones this role cannot use are marked 🔒.

    Pick “Claude Opus 🔒” and send anything.
    Model access denied — Claude Opus. No model was called.

    Access control covers which LLM may run, not just which data it may reach.

  5. Move a boundary while the app runs

    Sign in as Super Admin and grant the analyst payroll:

    Give the analyst role access to payroll.

    Sign back in as Analyst and ask "Show me employee salaries." It is now allowed. No restart and no re-seed — permissions are read fresh from the database on every message.

  6. Open the access control console

    Still as Super Admin, open Access control in the sidebar. Three tabs — Tools, Data (rows, datasets and columns) and Models. Every control calls the same tools the chat agent uses, so both surfaces share one audit trail.

The five roles

Each sees a different slice of the same database, along four axes at once.

Sign in asModels (best first)RowsColumns withheld
supervisor Sonnet · Haiku · Gemini team Why someone is on leave
analyst Haiku · Gemini all Email, all payroll figures, reviewer and comments, leave reason
hr Sonnet · Haiku · Gemini all Bonus and deductions
admin Opus · Sonnet · Haiku · Gemini all None — reads everything, changes nothing
superadmin Opus · Sonnet · Haiku · Gemini all None — the only role that can change access

The supervisor account is linked to an employee record, so a row scope of team means themselves plus their four direct reports — 5 of the 12 employees.

Four gates, in this order

Those differences are not one check. A request passes four independent gates, each in a different place in the pipeline, and none of them is visible to the model.

  1. Model access before the planner runs Is the role allowed to use the LLM it asked for? A refusal here contacts no provider at all.
  2. Permission inside the tool, before any SQL May this role run this tool? A denied request issues zero SQL statements.
  3. Row scope inside each handler Whose records are in scope — everyone, one department, the caller's team, or only themselves.
  4. Column policy after the query, before the agent sees the rows Which columns survive, along with any total computed from a withheld one.

A scenario

Daniel Okafor is a senior backend engineer. He reports to Priya Sharma, who leads Engineering. Five people ask the assistant the same question:

What does Daniel Okafor earn?
Who is askingResultWhich gate decided
Priya
supervisor		 ANSWERED All four pass. She holds payroll:read, and Daniel is one of her four direct reports, so he falls inside her team row scope.
Sofia
analyst		 REFUSED Gate 2. No payroll:read, so no SQL runs. Even if it were granted, gate 4 would strip every salary column.
Grace
hr		 REFUSED Gate 2. HR manages people and leave, not compensation.
Alex
admin		 ANSWERED All four pass, for all 12 employees — but Alex cannot change anyone's access.
Dana
super_admin		 ANSWERED All four pass, and Dana is the only one who can move the gates themselves.

Now switch the question to "Who is on leave right now?" and the ordering inverts: Grace answers it and Priya is refused, because HR holds leave:read and a supervisor does not. There is no seniority ladder here — each role is a different shape, not a bigger one.

That is the whole argument. Five people, one assistant, one database, five different answers — and not one of those differences was decided by the model.

Worth noticing

  • Every attempt is logged — allowed and denied alike, model refusals included. Ask an admin to show denied access attempts.
  • Admin reads the rules; only super admin changes them. That split is the entire difference between the two roles.
  • Even a super admin has a limit. Ask it to revoke its own payroll access and it refuses — the role is protected so nobody can lock everyone out.
  • Agents are not gatekeepers. Ask the analyst agent for salaries and it will reach for the payroll tool. The tool is what stops it.
  • Hiding the menu item is presentation, not security. An admin calling the console endpoints directly still gets 403.
